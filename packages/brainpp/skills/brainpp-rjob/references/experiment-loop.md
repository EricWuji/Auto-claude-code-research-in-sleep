# 在 rjob 上进行研究迭代

## 范围和停止条件

从用户请求确定问题、基线、数据、评价指标、可改范围、资源规格，以及轮次或累计运行时间等停止条件。能从已有说明推导的选择自行落实；缺少必要输入时继续代码检查和准备，仅询问影响执行的项。

明确授权 GPU 实验后，在范围内自主提交、分析和修改，不每轮确认。未授权持续探索时不把一次 smoke 扩展为长期搜索。默认串行；并发或扩大资源须有对应任务授权，每个实验独立保存代码和结果。预算包含失败尝试与仍运行任务，不只统计有效结果。

正式实验把训练写入共享目录的启动 Bash 脚本，通过 `rjob submit ... -- bash /共享路径/run.sh` 作为主命令执行，设置与预算匹配的运行上限。禁止使用 SSH 连接服务器或 worker，不启用 sshd，不创建保活任务。达到预算、用户停止或发生需外部处理的确定性故障时，不再创建新任务，处理本次仍占资源的任务并保存阶段结果。不要因查询失败重复提交。

## 代码和环境

在共享用户目录下采用以下结构，适配已有项目组织：

```text
user/wuyinqi/
  code/<project>/
  envs/<environment-version>/
  outputs/<run-id>/
    source/          本轮代码快照
    run.sh
    manifest.json
    train.log
    metrics.json
    figures/
```

修改工作代码后，提交前冻结本轮代码。可导出已提交版本；存在未提交修改时用受控副本或记录补丁及内容哈希，不能只记录 commit 却运行 dirty tree。复制限于实际项目文件，不复制整个 GPFS、数据集或凭据。入口指向快照，工作目录后续变化不能影响已提交或排队的实验。

共享 conda 环境也影响其他任务。修改代码时复用已验证环境；修改依赖时建立新环境版本或确认没有使用者。记录真实 Python 路径、包版本和激活步骤。验证 import torch、编译 CUDA 版本、CUDA 可用性和可见卡数；历史 smoke 无 torch，不能代替这项验证。

## 每轮循环

1. 基于证据提出可检验改动，尽可能让变化可解释，先做相关低成本本地检查。
2. 准备源码快照、配置、独立结果目录和脚本，记录资源与预算，使用指定 image、mount 和授权规格。
3. 提交并记录完整任务 ID，用 `rjob get` 每隔 20～60 秒查询状态，任务总体状态为 `Succeeded` 才表示执行成功完成；结合日志，不把创建成功当成程序成功。
4. 从共享目录读取指标、JSON、CSV、图片和错误信息。所有需要保留的结果必须写入共享 mount；这套 pipeline 不自动返回训练控制台输出，日志和诊断信息必须在启动脚本中重定向到 mount 文件；额外诊断通过下一次启动脚本采集。stdout 中的 JSON 不自动成为独立文件。
5. 核对指标有限、运行完整、评价协议一致，与基线在相同数据划分和设置下比较。需要时补充种子或重复验证，不把失败、部分训练或缺失指标当成改进。
6. 确认 `Succeeded` 后保存日志、结果和判断，用 `rjob delete` 删除本轮任务，再决定下一轮或结束。失败任务先保存证据再清理并修复。保留最优代码和证据，不以最新一次结果覆盖基线。

`manifest.json` 至少记录：run ID、完整任务 ID、假设及改动、源码版本和 dirty 修改证据、conda 前缀、关键包版本、image tag、启动命令、资源、配置及种子、指标方向、输出路径、时间和最终状态。按需要补充其他环境信息。

## 结果与收尾

每轮结果目录唯一，避免覆盖。程序写完指标后将完成标记写入 mount 文件；读取运行中指标时用临时文件加原子 rename 或容忍正在写入的不完整内容。看到保存路径后确认文件存在且可解析。

图片用当前图像查看工具；检查 checkpoint 时使用真实 conda 环境，不假设系统 Python 有 torch。区分主机内存 OOM 和 GPU 显存 OOM，不把退出成功等同于科学结论成立。

维护可继续的研究记录：基线和最佳指标、各轮改动、任务状态/ID、结果路径、剩余预算和下一步。已完成任务保存结果后用 `rjob delete` 删除；需要中断时只处理本次创建的任务，不删除共享结果或操作其他人的任务。对仍运行的任务明确说明，不能宣称会话结束后持续自主监控。
